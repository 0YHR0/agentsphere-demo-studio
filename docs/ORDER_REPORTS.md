# 电商订单报表 Agent：CPU 强化学习选择工具

打开 `http://127.0.0.1:8766/#scenario/order_reports`，客户场景默认推荐本案例。CPU RL统一使用订单报表业务案例。

## 把演示串成一个业务场景

电商运营每天需要核对订单销售、退款和净额。有时是400行的日常快报，有时是60,000行的月度商品分类汇总，有时是20,000行、2,000个客户的退款对账。报表必须算对，同时希望减少计算时间和内存。

Agent 有四个预先实现的工具：整表读入Python、逐行流式Python、1024行分块归并、导入SQLite后SQL聚合。它们计算相同的业务结果，并非用错误工具制造RL优势。模型学习的是“哪种工具适合哪类工作”，不学习编写程序。

**客户报表需求 → 策略选工具 → AgentSphere运行 → 主机验证报表、计算成本奖励 → CPU更新路由参数 → 新文件检验 → 保存重载和回收。**

本案例使用确定性合成订单，不读取真实客户数据、不解析任意自然语言、不支持任意CSV上传。页面中的客户请求是业务讲解文案，实际输入为预设的结构化任务类型和数据规模。训练是12参数上下文bandit，非LLM/Miles训练；进阶Miles入口另行保留。它展示环境反馈如何驱动工具路由优化，不包装成完整的生产报表系统。

## 准备与操作

需要连接客户自己的AgentSphere API/Gateway，并填写本场景专用的Ready `Template ID:Build ID`。镜像需Linux、Python 3、SQLite和resource标准库，现有sandbox用户可写/tmp。推荐已验证的 [官方Python模板](PYTHON_TEMPLATE.md)。不需要GPU、PyTorch或外部模型Key。

| 步骤 | 实际执行 | 可展示的证据 |
|---|---|---|
| 准备订单环境 | SDK创建独立沙箱、检查Python/SQLite/UID、上传工具/生成器/受限runner | 本轮Sandbox ID、版本与工具源码hash |
| 测初始与规则 | 3份校准CSV上，初始策略及固定规则各执行一次 | 6次正确性/时间/RSS，不用于参数更新 |
| 训练路由 | 默认12轮，每轮每类任务采样2次，真实运行后更新CPU参数 | 72次执行、reward、梯度和更新前后参数hash |
| 留出对照 | 2份新文件/任务、2次交错重复，分别测初始/规则/RL | 每路由12次，共36次真实执行；包括相同动作的重新执行 |
| 保存重载 | 从磁盘重载模型，再实测3份报表，导出模型及评估JSON | 参数/动作一致，报表正确；时间与reward允许自然变化 |
| 回收 | 仅删除本场景本轮沙箱并确认404 | 模型、证据、客户模板及其他场景保留 |

顶部主按钮每次只执行一步。“仅准备状态”不会暗中训练。训练批次异常不更新参数；中断后可接续已提交的批次。变更模板、运行用户、轮数、种子、学习率或工具代码需先清理再开始新一轮。已不存在的沙箱不能被新实例冒充。

页面分成“对照组”和“强化学习”两块：左侧是不更新概率的初始策略与人工规则，右侧是训练轮数、执行次数及最终新文件成绩。对照组可切换训练前校准集基准和最终同文件复测；校准集分数不能与右侧验证集成绩直接相减。最终复测完成后默认展示同一验证集，避免混淆不同文件的测量。

“训练过程”可选任意已完成轮次，查看本轮6次执行的任务、工具、得分、耗时和峰值内存，或切换查看3类任务×4种工具的更新后概率及本轮变化。pp是百分点，变化相对本轮更新前；初始概率均为25%。训练平均分与最终验证分分开显示。

概率变化由主机只读视图使用已记录的实际奖励复算，逐轮验证更新前后参数SHA256及梯度，最终核对当前模型SHA256；不重新执行沙箱、不补造性能数据。证据不一致则不展示概率推算值。视图不会修改会话或再次提交训练。

评分说明收进“评分规则”，配置和SDK分步操作默认折叠。SDK步骤也分为对照组与强化学习两块，代码从各步骤实际函数提取；基准SDK直接显示校准集基准值，多轮SDK显示逐轮得分和最大单项概率变化。

默认设置在首次实测前固定为12轮、学习率6、种子7，不重跑种子来挑选获胜结果。

## 数据与正确性

CSV字段：order_id、customer_id、category、quantity、unit_price_cents、refund_cents、status。取消订单排除；已支付订单按数量×单价计算销售额，扣除退款得到净额。所有金额使用整数分，避免浮点货币误差。

可以先离线生成一份实际CSV并运行同一工具，查看业务输入输出；以下命令不访问云端、不参与训练：

```bash
python examples/generate_orders_csv.py --profile monthly --seed 47 --output orders.csv
python studio/scenarios/order_reports/strategies.py orders.csv stream category
```

生成器拒绝覆盖现有文件。生成的数据仅为本案例合成订单，不是真实客户订单。

主机独立算术参考答案验证所有总额、已支付订单数和所有分组；不只验证抽样或报表hash。JSON数值类型也严格匹配，不允许float/bool冒充整数分。报表预览是已验证结果的节选，完整正确性检查仍覆盖所有分组。

CSV生成在沙箱内完成，不计入策略处理耗时。每份CSV按实际内容SHA256与主机验证，工具与runner源码hash每批核对。参考报表与reward计算代码不上传到沙箱。只缓存确定性输入hash/参考答案以减少本机开销，**不缓存策略执行、时间、RSS或reward**。

数据划分：校准种子101–103；训练种子200000+round×3+profile_index；留出固定种子900001和900107。评估检查实际文件hash未出现在训练中。留出文件属于未训练的相同工作类型，不能称为对任意CSV/新任务的泛化测试。

## 奖励与测量

```text
report_incorrect / candidate timeout / nonzero exit -> reward = 0
report_correct -> reward = 1 / (1 + 0.6*time_s/time_scale + 0.4*peak_RSS_MiB/memory_scale)
```

三个任务的归一化标尺在实验前固定：日常(.25秒,32MiB)、月度(1.5秒,48MiB)、客户(.8秒,48MiB)。它们用于连续成本归一化，不是超时/内存硬限制，不随本轮最佳工具重新调整。

受限子进程硬限制为10秒墙钟、11秒CPU、256MiB地址空间以及输出/文件数/进程数限制。每次新进程执行，结束清理进程组。Linux wait4记录wall time、CPU time和ru_maxrss；RSS按Linux KiB转换为MiB。墙钟包括子进程启动、Python加载、读CSV、计算和写JSON，不包含CSV生成、SDK网络、宿主端校验，也不等于整个沙箱/cgroup内存。SQLite为内存数据库，导入和查询都在计时内。

SDK/网关/沙箱/runner错误、缺结果、坏指标或hash不一致属于基础设施失败，不伪装成模型零分。只有成功取得整批观测后才提交REINFORCE更新。

## 固定规则与公平对照

规则在实验前冻结：≤2000行用整表；商品分类用流式；客户对账用SQLite。初始策略为零参数均匀分布，其贪心tie-break固定选择整表；评估不随机挑选更好的初始动作。

相同文件上交错运行三种路由，第二次反转顺序。即使两个路由选择同一种工具，也重新执行，不能复制同一性能结果。保留全部观测，展示正确率、平均时间、平均峰值RSS、平均reward。训练后的模型只使用训练reward更新，不读取留出成绩。

页面将平均reward差>.01/<-.01/其余分别显示更高/更低/接近，这是展示阈值，不是统计检验。两次重复不能证明显著性；页面保留落后或接近规则的结果。场景的验收是业务计算正确、训练与新文件对照闭环真实，不预设RL必须获胜。

## 交付与复用

“保存重载”将本机 `order-router-model.json` 与 `order-report-evidence.json` 写入忽略目录的本轮artifacts。页面下载的证据JSON包含model字段（实际权重/超参数/hash）以及每次留出和重载实测。时间有噪声，重载核对参数和动作一致、报表正确，不要求两次性能reward相等。

离线推断：

```bash
python examples/order_router_predict.py --model /path/to/order-router-model.json --profile monthly
# 也可传页面下载的order-report-evidence.json，会读取其中model字段
```

CLI与页面使用同一引擎：依次执行orders_prepare、orders_baseline、orders_train、orders_evaluate、orders_checkpoint、orders_cleanup。CLI默认.local/cli是独立配置，先配置本机连接和orders_template_ref。

## 2026-11-23 首轮实测

用户自有贵阳一区域、官方Python 3.12.16模板、sandbox用户；锁定SDK/官方patch不变。6步全部通过，约139.40秒。12轮训练提交72次真实观测；留出对照36份报表全部正确，模型重载3份也正确；测试沙箱删除404，Ready模板保留。

| 路由 | 留出报表正确 | 平均reward | 平均进程时间 | 平均峰值RSS |
|---|---|---|---|---|
| 初始整表策略 | 12/12 | 0.77149 | 91.66ms | 26.90MiB |
| 固定规则 | 12/12 | 0.83383 | 91.33ms | 14.43MiB |
| RL策略 | 12/12 | 0.83581 | 83.27ms | 14.61MiB |

结论：本轮RL降低了相对初始整表策略的成本；与固定规则reward差约0.00199，按预定阈值归为接近，未证明额外收益。不能把小幅时间差当作显著或生产优势。原始证据只在本机忽略目录，不预置到客户发布包中。

### 第二轮：正式页面逐步点击实测

同一预先固定的12轮/学习率6/种子7，通过正式页面“下一步”完成六步，未换种子或挑选更好的一轮。留出36份报表、重载3份均正确，沙箱回收404；页面保留本轮真实结果，客户下载的源码包仍没有这些运行记录。

| 路由 | 留出报表正确 | 平均reward | 平均进程时间 | 平均峰值RSS |
|---|---|---|---|---|
| 初始整表策略 | 12/12 | 0.77153 | 90.90ms | 26.94MiB |
| 固定规则 | 12/12 | 0.83411 | 90.62ms | 14.47MiB |
| RL策略 | 12/12 | 0.83597 | 82.72ms | 14.65MiB |

reward差约0.00186，仍归为接近。六个后端步骤累计执行约110.80秒；含页面操作、阅读和等待的总时间约229.27秒，两者不能混同。两轮均未证明RL胜过已有规则，但完整展示了策略如何消费真实环境反馈、更新和接受独立对照。
